# Workshop-Site — Information Architecture & Per-Page Audit

_Status: **approved 2026-07-25**. No page has been rewritten yet; this document is the work order for that rewrite. Every claim below traces to the audited corpus, the prerequisite-gap lenses, or a file read out of `Workshop-Code` / `2027-Template` with `gh api`. Anything I could not confirm against a real file is marked **TODO(verify)** rather than guessed._

_Ground-truth rule used throughout: when a page and a branch disagree, the branch wins. When a branch and the `2027-Template` disagree, the template wins for API spelling and the branch wins for "what the student has on disk at this lesson."_

**Hardware assumption (settled 2026-07-25).** The workshop supplies the hardware, and teams following along build the same mechanism. So every page assumes **CTRE hardware is present** — Kraken/TalonFX, CANcoder, CANivore, Phoenix 6. Two consequences for the rewrite:

- **Write no vendor alternatives.** No "if you're using a SparkMax instead…", no vendor-comparison asides, no abstraction layer to accommodate other motor controllers. Name the actual device.
- **There is no no-hardware path, and that is the answer, not a gap.** This resolves §10 question 4 in favour of option (b): state the hardware requirement plainly on `/prerequisites` and stop treating the missing sim-only route as something to build. "Hardware simulation" on `/running-program` drives real motors over a CANivore and is not a physics sim — say so, early, rather than letting a student discover it at lesson 13.

## 1. What changes and why

The Commands section splits in two. First, basic inline commands — `runRepeatedly` / `.named(...)` / trigger bindings, branch `2-Commands`. Then a first-class **Chaining Commands** lesson — `Command.sequence` / `Command.race` / `.withTimeout` — that becomes the default composition dialect every page uses from that point until the coroutine lessons at the end.

Today all of that composition vocabulary is crammed into `/command-framework`, which sits _third_ in Workshop #1. That is before any Mechanism, any Command, any trigger binding, and before a single line of Java has appeared anywhere on the site.

Coroutines are used on **six pages** and taught on **zero**. They get two new lessons at the end (`6-Coroutines`, then the advanced `7-InlineCommands` / `DriveToTagInline`), so the dialect order finally reads basic → chaining → coroutines → state machines → advanced coroutine (`7-InlineCommands`, #30).

The two coroutine lessons are **not adjacent**, and that is deliberate. #29 `/state-based` sits between them because `6-Coroutines` and `7-StateBased` are both mechanism-track branches one commit apart, while #30's `7-InlineCommands` sits on the swerve track. Running #28 → #29 → #30 means one mechanism-track checkout and then one swerve-track checkout. Moving #29 to the end would make the student switch tracks twice.

That argument is about today's two-track repo. If §11.0 is taken, the tracks disappear — `14-Coroutines`, `15-StateBased` and `16-DriveToTagCoroutine` become three consecutive links of one chain and there is no track to switch. The ordering still holds, on the simpler ground that #30 is the hardest page on the site and belongs last, but the reason above stops applying. Keep it only while the repo stays as it is.

Three Workshop-Code branches own no page at all (`5-GettersAndSetters`, `6-Coroutines`, `7-InlineCommands`), and six of the fourteen branches are referenced by no `branch=` prop anywhere on the site. `/state-based` points at a branch that returns 404, so that embed is dead in production right now.

The page order is re-cut to follow branch order **on the mechanism track, where branch order is genuinely linear**. On the swerve track it cannot be, because that track forks — see §2 and §3. The re-cut pulls `/vision-shooting` and `/advanced-drive-to-point` out of Advanced Topics into their real positions in the swerve sequence, and moves `/pathplanner` to the end of Workshop #2, where the student finally owns a self-finishing drive command to sequence.

A new **"The Java You Need"** page lands between `/project-setup` and `/command-framework`, because the site currently tells students Java is optional and then opens with `runRepeatedly(() -> setPosition(SCORING_POSITION)).named("scoring (hold)")`.

Two option-survey pages (`/logging-options`, `/vision-options`) merge into the implementation lessons they precede. No existing URL changes — the only two slugs that stop rendering get 308 redirects.

## 2. Proposed page order

### What `lessons.ts` and `Sidebar.tsx` must change

The four `SectionMeta` entries in `src/data/lessons.ts:40-45` (`main` / `workshop1` / `workshop2` / `advanced`) keep their ids **and** their titles. **`SECTIONS` does not change.**

Two other things do change, and an earlier draft of this plan wrongly said they did not:

1. **`Lesson` gains `optional?: boolean`.** `src/data/lessons.ts:19-27` currently defines `Lesson` as exactly `{ slug, title, shortLabel?, section }`. There is no optional flag. `Sidebar.tsx` renders only `getSidebarLabel(lesson)` at lines 324 and 476, with no branch for any per-lesson modifier. **Three** pages carry the flag, not two: `/mechanism-cad` (#4), `/ai-coding-assistant` (#14) and `/vision-shooting` (#24). Marking them optional is a UI promise, so the interface and the sidebar render both have to change. Without that change an implementer following this section ships a linear 30-step sidebar in which the 3D-printer gate is still a required step and the dead-end flywheel branch still reads as a required Workshop #2 lesson — which is the exact claim the ordering argument at #24 and §3's swerve-track row rest on.
2. **The `Class` column below is an authoring convention only.** `lesson` / `prerequisite` / `reference` never reaches the UI and needs no `kind` field on `Lesson`. It tells the writer what tone and what verification section the page needs. If the team later wants it visible, that is a second `kind?: "lesson" | "prerequisite" | "reference"` field plus a second Sidebar change — not required by anything here.

The `LESSONS` array itself is fully rewritten: six new entries, six moved entries, two removed.

### Two shapes of group, and why the difference matters

On `2-Commands` **every** mechanism command is a hold, including `stop()` (`runRepeatedly(motor::stopMotor).named("stop (hold)")`). Teach both shapes and say which one to prefer.

**Shape A — the group is a hold** (last step is a hold, so the group never finishes). Bind with `whileTrue(...)` and pair it with `whileFalse(...)`. This is what `5-GettersAndSetters` does and what the template's `TeleopOpMode` does:

```
driver.y()
    .whileTrue(
        Command.sequence(
                arm.runFast().withTimeout(Seconds.of(1.0)),
                flywheel.runFast())
            .named("Lift Then Spin (hold)"))
    .whileFalse(flywheel.stop());
```

**Shape B — the group finishes.** Every step has an ending, so the group ends. When it ends, the mechanisms fall back to `Mechanism.idle()`, the implicit default command — and `idle()` at `LOWEST_PRIORITY` **issues no motor output and does not zero the last control request**. Phoenix keeps driving the last request it was given. That is exactly why `2-Commands` binds `onTrue(arm.runFast()).onFalse(arm.stop())` and why `stop()` exists at all. So a finishing group must end with explicit stop steps, or you must set a real default command on the mechanism. Neither mechanism-track branch sets a default command, so at this point in the course prefer Shape A.

### "Did it work?"

1. Bind the Shape A routine in `TeleopOpMode`'s constructor with `whileTrue(...).whileFalse(flywheel.stop())`.
2. Launch the simulator the way #13 taught (`gradlew simulateJava`, click Enable).
3. Hold Y. **You should see:** the arm runs for exactly the time you set, stops, _then_ the flywheel starts. Not both at once.
4. Keep holding Y past the arm's timeout. **You should see:** the flywheel keeps spinning and does not stop on its own. That is correct — the last step is a hold, so the whole group is a hold.
5. Release Y. **You should see:** the group is cancelled and the `whileFalse(flywheel.stop())` binding stops the flywheel. **If the flywheel keeps spinning after release**, you left off the `whileFalse` — nothing else on this branch will stop it, because an unclaimed mechanism runs `idle()`, and `idle()` commands nothing.
6. **Now reproduce Shape B on purpose.** Replace the whole group with a single finishing step that leaves the arm driving: `arm.runFast().withTimeout(Seconds.of(1.0))`, bound with `whileTrue`. (No `.named(...)` after `.withTimeout(...)` — `runFast()` is already named, and §8 records `/command-framework:244` re-naming a built `Command` as one of that page's non-compiling examples.) Hold Y for two seconds. **You should see:** after one second the command ends — and **the arm keeps moving anyway**. That is Shape B. The group finished, no command claims the arm, `idle()` took over at `LOWEST_PRIORITY`, and `idle()` issues no output and does not zero the last request, so Phoenix keeps applying the 6 V you last sent.
7. **Now fix it.** Wrap the step back into a sequence and give it a real ending: `Command.sequence(arm.runFast().withTimeout(Seconds.of(1.0)), arm.stop().withTimeout(Seconds.of(0.5))).named("Lift Then Stop")`. **You should see:** the arm runs for one second, then holds still, then the routine ends and the arm stays put. That is Shape B done correctly — the explicit stop step from the rule above. The alternative fix is a real default command on the mechanism, which no mechanism-track branch sets (#20 is where you first see one).
8. _(TODO(verify))_ Whether the driver-station / Elastic command list surfaces the group's `.named(...)` string while it runs. `/command-framework:112` asserts it ("if a stuck routine is sitting on a `(hold)` command on the dashboard or in the log, that's the bug") and three branch source files repeat the claim in comments, but nothing in the verified ground truth confirms the dashboard behavior. A `DataLogManager.log(...)` marker is a confirmed-in-repo alternative — `7-StateBased` uses exactly that in `onEnter`/`onExit`.

### Backing branch — none exists

No Workshop-Code branch teaches this content at this point in the sequence:

- `2-Commands` has **zero** composition — its entire `TeleopOpMode` is three `onTrue(x).onFalse(y)` pairs.
- `5-GettersAndSetters` is where `Command.sequence` / `.until` / `whileTrue` / `whileFalse` debut, but it sits **after** `3-PID` and `4-MotionMagic`, so checking it out here would hand the student PID and Motion Magic changes they have not done.
- `Command.parallel` does not appear in Workshop-Code until `7-StateBased`.
- `Command.race` appears in Workshop-Code **nowhere at all**. The only verified use in either repo is `DriveStowDriveChainedOpMode.java` in the template. (Confirmed by reading every branch tree and the composition-bearing files; GitHub code search indexes only default branches and is not usable here.)

**What would need to exist:** a branch between `2-Commands` and `3-PID` that (a) switches `TeleopOpMode`'s bindings from `onTrue`/`onFalse` to `whileTrue`/`whileFalse`, and (b) adds one composed routine using only the voltage commands `2-Commands` already has — the Shape A block above — plus one `Command.race(step, hold)` example. That is a lesson-sized diff of one file.

**Naming is a real decision, and §11.0 makes it:** the branch is `03-Chaining`, sitting between `02-Commands` and `04-PID`. See §11.0 for the whole mapping and §11.1 for the content. Interim if no branch is created: run this page branch-free against the code the student already has from `2-Commands`, with `DriveStowDriveChainedOpMode.java` as the read-only reference. That works, but it becomes the only lesson in Workshop #1 with no diff to open, and this audit shows unanchored pages are exactly where drift happens.

**Why one chain and not two.** Four facts decide it.

1. **The numbers are ambiguous today.** Two branches share every number from 1 to 7. 2. **The graduation target already holds both tracks at once.** `2027-Template@2027-dev` ships `subsystems/arm/Arm.java`, `subsystems/flywheel/Flywheel.java`, `subsystems/CommandSwerveDrivetrain.java`, `subsystems/DriveMechanism.java` and `subsystems/vision/Limelight.java` in one tree. An accumulating chain converges on that. The current split never does — a student who finishes both tracks has never had a checkout that looks like the robot they graduate to.

Zero-padded, because sixteen branches sort lexicographically in `git branch`, `gh`, and every branch dropdown: unpadded, `10-DynamicFlywheel` sorts between `1-Subsystem` and `2-Commands`.
